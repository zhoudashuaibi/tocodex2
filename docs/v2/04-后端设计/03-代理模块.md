# 04-03 代理模块

## 1. 需求

- 批量输入代理（每行一个，可带备注），导入去重。
- 一键测试全部/单个的**连通性**。
- 所有需要用账号 auth 信息请求 OpenAI 接口的操作（登录、重新授权、刷余额等），**随机**从「能连通」的代理中挑一个使用；没有可用代理时的行为由 `engine.config.strict_proxy` 决定：默认 `true`（无可用代理则任务直接失败，**绝不本机直连**，防止服务器 IP 暴露触发封号），显式设为 `false` 时才回退本机 IP 直连。

## 2. 数据模型

见 [02-数据库设计.md](../02-数据库设计.md) `proxies` 表。要点：

- `url_enc` 加密存完整代理 URL（含账密）；`url_hash = sha256(归一化URL)` 用于唯一约束与查重；`display_url` 脱敏展示。
- `status`: `unknown`（未测）→ 测活后 `alive / cf_challenge / dead`；测试进行中短暂 `testing`。
- `rotatable`：导入时用 `proxySupportsSessionRotation`（v1 tls-transport.mjs:412-421）判定（用户名含 `-sid-XXXX-t-20` 或密码含 Kookeey `-JP-数字-20m` 会话字段），决定风控时能否换会话重试。
- `fail_count`：**任务运行中**代理连接失败累计（与测活的 `consecutive_dead` 分开记账），成功一次清零；达到 `engine.config.proxy_fail_threshold`（默认 3）→ 自动置 `dead`。

## 3. 导入（POST /api/v1/proxies/import）

```
请求: { "text": "http://u:p@1.2.3.4:8080----标签A\nsocks5h://u:p@proxy.example.com:1000\n..." }
```

解析规则（每行）：

1. 去空白行/注释行（`#` 开头）。
2. 按 `----` 分割，第一段为 URL，第二段（可选）为备注。
3. URL 规范化：`new URL()` 校验，协议必须 `http/https/socks5/socks5h`（复用 v1 `normalizeProxyUrl` 语义，console-server.mjs:3991-4004）；无协议前缀时默认补 `http://`。
4. 计算 `url_hash`；与库内或本批内重复 → 计入 `duplicates`（已存在的更新 label，如传了新值）。

响应：

```jsonc
{
  "created": 18,
  "duplicates": ["http://u:***@1.2.3.4:8080"],
  "invalid_lines": [{ "line": 7, "raw": "ftp://x", "reason": "不支持的协议" }]
}
```

导入完成后前端提示「是否立即测活」。

## 4. 测活

### 4.1 判定标准（与登录预检同一口径）

「能连通」的定义 = **通过该代理以 Chrome TLS 指纹访问 chatgpt.com 首页成功且不是 Cloudflare 风控页**——这正是 v1 登录前 `prepareProxy` 的预检逻辑（protocol-login.mjs:322 → tls-transport.mjs:89-160），保证「测活通过的代理 = 登录可用的代理」。

| 结果 | 判定 |
|---|---|
| `alive` | HTTP 200-399，且 `isRiskControlResponse` 不命中；记录 `last_latency_ms` |
| `cf_challenge` | 连接成功但命中风控页（`cf-mitigated: challenge` / 403+html / challenge 关键字）——代理通但出口被 CF 盯上，**不参与随机选路** |
| `dead` | 连接失败/超时（默认 15s）；记录 `last_error` |

`cf_challenge` 与 `dead` 都不算「能连通」；`consecutive_dead` 达 2 次才置 dead（首次可能是抖动，置 `unknown` 复测机会——简化实现也可直接 dead，在实现时取其一并写入测试）。

### 4.2 实现：短生命周期测活 worker

复用 `core/tls-transport.mjs` 的 `TlsFingerprintTransport`，**每批测活 spawn 最多 5 个独立实例**（每个实例一个 Python 子进程；不复用登录任务的长驻 worker，测完即 `close()`）：

```js
// test-worker.js 伪代码
export async function testProxies(proxies /* 待测行 */, onResult) {
  const queue = [...proxies];
  await Promise.all(Array.from({ length: Math.min(5, queue.length) }, async () => {
    const transport = new TlsFingerprintTransport({ profile: 'chrome146' });
    try {
      while (queue.length) {
        const p = queue.shift();
        const t0 = Date.now();
        try {
          await transport.configure(p.url, { force: true });
          const res = await transport.fetch('https://chatgpt.com/', { timeoutMs: 15000 });
          const latency = Date.now() - t0;
          const status = isRiskControl(res) ? 'cf_challenge' : (res.status < 400 ? 'alive' : 'dead');
          onResult(p.id, { status, latency, error: null });
        } catch (e) {
          onResult(p.id, { status: 'dead', latency: null, error: String(e.message || e) });
        }
      }
    } finally { await transport.close(); }
  }));
}
```

- 结果即时逐条 UPDATE，前端轮询 `GET /api/v1/proxies` 看实时状态变化（`testing` → 结果）。
- `POST /api/v1/proxies/test` `{ids?}`：ids 省略 = 全部 `unknown + dead + cf_challenge`（`alive` 不重测，除非单条显式指定）；单条测试同端点传单个 id。
- 服务器同时只允许一个测活批次进行中（重复触发返回 409），避免 Python 进程堆积。

## 5. 随机选路（selector.js）

```js
export function pickRandomAliveProxy(db) {
  const row = db.prepare(
    "SELECT id, url_enc FROM proxies WHERE status = 'alive' ORDER BY RANDOM() LIMIT 1"
  ).get();
  if (!row) return { proxyId: null, proxyUrl: null };      // 本机直连
  return { proxyId: row.id, proxyUrl: decrypt(row.url_enc) };
}
```

调用点（任务引擎 launcher，见 04-06）：

| 场景 | 选路 |
|---|---|
| 账号 `credentials.proxy_url` 非空（v1 兼容：账号固定代理） | 用账号代理 |
| 否则 | `pickRandomAliveProxy()`；无 alive → 受 `strict_proxy` 管控（默认拒绝直连，登录/余额任务直接失败，错误码 `NO_ALIVE_PROXY`；仅 `strict_proxy=false` 时以 `proxy_id=null` 直连） |

余额刷新（batch-refresh-balance）同样走随机代理；上传前补查余额在无可用代理且开启 strict 时跳过补查（保持账号原名上传）。

## 6. 失败降级

任务引擎收到子进程 `PROXY_CONNECTION_RETRY` 重启时（见 03 §5.4）：

1. `UPDATE proxies SET fail_count = fail_count + 1 WHERE id = ?`（该任务选中的代理）。
2. `fail_count >= threshold(默认3)` → `status='dead'`, `last_error='任务连接失败累计'`，本任务后续重启换用新随机代理（重新 `pickRandomAliveProxy` 排除死掉的）。
3. 任务最终成功 → `fail_count = 0`。

## 7. API 摘要

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/v1/proxies` | 列表（分页/按状态筛选）+ 统计 `{alive, dead, cf_challenge, unknown}` |
| POST | `/api/v1/proxies/import` | 批量导入 `{text}` |
| PATCH | `/api/v1/proxies/:id` | 改备注 `{label}` |
| DELETE | `/api/v1/proxies/:id` | 删除单条 |
| POST | `/api/v1/proxies/batch-delete` | `{ids[]}` |
| POST | `/api/v1/proxies/test` | `{ids?}` 触发测活（无 ids=全部非 alive） |

**GET 返回的代理一律脱敏**（`display_url`），完整 URL 只在服务端内部解密使用；前端不需要也不应拿到明文代理凭证。
