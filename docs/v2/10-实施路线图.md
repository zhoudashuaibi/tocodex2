# 10 实施路线图

按里程碑推进，每个里程碑有明确验收标准（演示脚本级）。**M2 是最大风险点（协议改造），最先验证。**

```
M1 骨架 ──► M2 核心链路 ──► M3 代理+备用池 ──► M4 codex2api+废弃池 ──► M5 打磨发布
   1周         2周              1周                 1.5周               1周
```

## M1 骨架（约 1 周）

**范围**：monorepo 脚手架、SQLite+迁移、认证会话、前端壳（登录+布局+空页面路由）、部署流水线雏形。

任务清单：

1. npm workspaces 初始化（server / web）；web 从 shadcn-admin degit 并裁剪（06-01 §2）。
2. `lib/db.js` 迁移执行器 + `0001_init.sql`；`lib/crypto.js` 信封加解密 + 单测。
3. auth 模块：登录/登出/session/限流/改密 + Cookie（04-02 全部）。
4. Fastify 装配 + 认证 hook + 统一错误 + health + 静态托管 SPA。
5. 前端：登录页、`_auth` 布局（侧边栏 7 项）、各页面空态占位、api client。
6. Dockerfile/compose 跑通（本地 build）。

**验收**：
- `docker compose up` → 打开页面 → 首访设置密码 → 登录 → 看到侧边栏与空页面。
- 刷新页面不要求重输密码；30 天 Cookie 属性正确（DevTools 验证 HttpOnly/SameSite）。
- 连续输错 5 次密码锁定 15 分钟；重启容器锁定仍在。
- 未认证 `curl /api/v1/jobs` 返回 401；`sqlite3` 查看 settings 密文。
- 改密码后旧会话 401。

## M2 核心链路（约 2 周，风险最高）

**范围**：`--json-events` 改造、任务引擎、主号池手动添加账号→登录→token 入库全链路、任务中心页面。

任务清单：

1. **protocol-login.mjs 改造**：`--json-events` 模式 + stdin JSON 输入（03 §8 规范）；CLI 原模式回归测试。
2. `core/` 迁移 + 为测活抽出共享 `isRiskControlResponse`（或 export）。
3. 任务引擎：调度器、launcher、events 纯函数表、auto-input（先做人工输入 + Outlook 自动收码）、代理风控重启、checkpoint、日志落盘、重启恢复（04-06 全部）。
4. accounts 模块最小集：`POST /accounts`（手动添加）、join 语义（此时账号直接进主池流程）、`GET /accounts?pool=main`。
5. 前端：任务中心页（列表/日志/内联输入/取消）、主号池页（列表/删除/导出）。
6. 单测：events 状态机表全分支；mock 子进程（复用 v1 `test/mock-protocol-login.mjs` 思路）跑引擎集成测试。

**验收**：
- 页面添加一个真实 Outlook 账号 → 任务跑通 email_otp 自动收码 → completed → 主号池出现该号、余额已查、tokens 密文入库。
- 人为断点（改错密码）→ awaiting_input → 行内输错 → 重试提示 → 正确后流程继续。
- 登录中途 `docker restart` → 任务自动回 queued 重跑；日志文件可看完整历史。
- 代理风控模拟（mock 返回 challenge）→ 观察 attempt 递增与会话重启 ≤10。
- CLI 原交互模式（不带 --json-events）人工跑一单无回归。

## M3 代理 + 备用号池（约 1 周）

**范围**：代理模块全部、备用号池导入/邮件初始化/加入主池。

任务清单：

1. proxies 模块：导入/测活 worker/随机选路/失败降级（04-03）。
2. accounts 扩展：import 四段解析 + 三重查重响应、mail-init（复用 outlook-mail）、join-main 流程（04-04 §2-3）。
3. 引擎接入随机选路（替换 M2 的直连/固定代理）。
4. 前端：代理列表页、备用号池页（含导入弹窗与重复提示文案）、dashboard 雏形。
5. 测试：import 解析单测（复用 v1 `test/outlook-mail.mjs` 思路）；测活 worker 对 mock HTTP 服务验证三类判定。

**验收**：
- 批量导入 20 条代理 → 一键测活 → 状态/延迟正确刷新；拔掉一条再测 → dead。
- 全部代理 dead 时登录任务直连成功（日志可见无代理）。
- 导入 30 条邮箱（构造：5 条与主池重复、3 条格式错）→ 弹窗准确显示「xxx、xxx 账户已在主号池中」与非法行；其余入池并自动初始化出余额/封禁。
- 备用池选 2 个号加入 → 登录成功出现在主号池、备用池消失（事件流水可查）；登录失败回备用池且错误可见。

## M4 codex2api + 废弃号池（约 1.5 周）

**范围**：codex2api 客户端/上传管线/监控巡检/自动修复/自动补号/废弃池流转。

任务清单：

1. codex2api client + config 存储（加密/掩码）+ test/groups/proxies 路由（04-05 §2、§5）。
2. 上传管线：查重索引、新增/替换分流、最少绑定代理分配、余额后缀、幂等键（04-05 §3）。
3. monitor：巡检循环、错误分类（可配置正则）、移废弃、自动重登修复、冷却、自动补号（04-05 §4）。
4. discard/restore/手动废弃 + 主池 remote_status 展示。
5. 前端：codex2api 管理页、废弃号池页、主号池上传配置弹窗、批量操作条全量。
6. 测试：**移植 v1 `test/proxy-autoselect-smoke.mjs`**（最少绑定代理 + 5h/7d 开关契约固化）；mock codex2api 覆盖新增/替换/监控分类三场景（复用 v1 mock 思路）。

**验收**：
- 配置 codex2api → 上传 3 个新号：远端新增 3、代理绑定均衡、`---N` 后缀正确；再上传同 3 号（改 token）→ 远端替换不新增、clear-error 生效。
- mock 远端注入 `account_deactivated` 错误账号 → 一轮巡检后主池该号进入废弃池（原因 banned_401）；注入 429 → rate_limited_429。
- 注入临时错误 → 自动重登修复成功（远端 PUT 新凭据）；构造修复连续失败 → 达上限移入 repair_failed。
- 自动补号：阈值 5、主池 3 → 巡检触发 2 个 join。
- 废弃页「移回主池」→ needs_reauth → 批量授权 → active。

## M5 打磨发布（约 1 周）

**范围**：dashboard 完整版、设置页全量、迁移脚本、备份脚本、文档、性能与安全自查。

任务清单：

1. dashboard 统计卡/图表/最近动态；设置页（改密/会话管理/取件端点/接码平台/引擎参数）。
2. `scripts/migrate-v1.mjs`（09 §2）+ `scripts/backup.mjs`。
3. 日志/任务 30 天清理任务；超时看门狗。
4. 全量回归（M1–M4 验收脚本串跑）+ 07 §9 安全自查清单。
5. README 更新、CHANGELOG、GHCR 镜像流水线（沿用 v1 workflow 改多阶段构建）。

**验收**：
- v1 真实数据目录迁移演练：主池/备用池数量对账一致、codex2api 配置带入、产物可下载。
- 在线备份 → 新容器恢复 → 全部数据可读。
- 安全清单全绿；一键镜像发布成功。

## 风险与对策

| 风险 | 对策 |
|---|---|
| json-events 改造触碰登录主流程 | 改造只在交互层插桩；保留原模式并做双模式回归；M2 最先行 |
| 上游 auth.openai.com 改版 | 与 v1 相同风险面；core/ 独立目录便于热修；协议文档（03）标注脆弱点 |
| sentinel SDK 升级破坏补丁锚点 | 每次跑 protocol-smoke；回退自研 VM 已是既有兜底 |
| codex2api 错误文案字段差异 | 分类正则可配置（settings）+ 多字段拼接匹配 |
| better-sqlite3 原生模块跨平台编译 | Docker 内固定 Debian slim + Node 22 预编译产物；Windows 开发需 VS Build Tools（README 注明） |
| 范围蔓延（v2 又变单体） | 模块边界评审：新功能必须落进既有 domain 目录或新增 domain，禁止加回「大一统文件」 |
