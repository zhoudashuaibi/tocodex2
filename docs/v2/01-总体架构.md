# 01 总体架构

## 1. 系统目标

toCodex2 v2 是一套部署在公网（HTTPS 反代之后）的 ChatGPT 账号池管理系统：

1. **代理列表**：批量导入代理，一键测活；所有需要请求 OpenAI 接口的操作（登录、刷余额等）随机选用存活代理，无可用代理时回退本机直连。
2. **三级号池**：
   - **备用号池**：导入 `邮箱----密码----clientId----refreshToken` 格式的 Outlook 账号，从邮件列表初始化邮箱名、初始余额、封禁状态；支持单选/批量加入主号池。
   - **主号池**：账号加入时执行邮箱验证码登录（复用现有核心协议），登录后通过接口获取实时余额；支持批量授权、批量上传 codex2api、批量获取余额。
   - **废弃号池**：codex2api 侧出现 401 封禁或 429 限流的账号自动移入（记录原因），也支持手动废弃与移回。
3. **codex2api 管理**：配置后端地址与管理员密钥；上传时可选禁用 5h/7d 自动暂停、并发数、优先级、负载因子、模型白名单、自动分配 codex2api 内已有代理；codex2api 已存在的账号替换凭据、不存在的新增。
4. **可用性**：页面密码保护但刷新不要求重输（30 天会话）；数据全量持久化，重启不丢；左侧菜单 + 右侧内容的经典后台布局。

### 非目标（v2 不做）

- 多用户/角色权限体系（单管理员密码）。
- 不改写 OpenAI 登录协议本身（协议层整体复用 v1）。
- 不做移动端专门适配（响应式可用即可）。

关键进程模型（与 v1 一致，刻意保留）：

```
Fastify 主进程
 ├── 任务引擎 worker（事件循环内调度，不单独开线程）
 │    └── spawn → node core/protocol-login.mjs --json-events ...   （每任务 1 个子进程）
 │              └── spawn → python core/tls_transport.py           （每任务 1 个 Python worker）
 ├── 代理测活 worker（并发 ≤5 个短生命周期 Python worker）
 └── codex2api 监控定时器（默认 5 分钟一轮）
```

子进程隔离是刻意设计：协议登录崩溃/卡死不影响主服务；Python worker 崩溃只影响单个任务。

### 3.2 允许的最小改造（行为不变）

1. **`protocol-login.mjs` 新增 `--json-events` 模式**（唯一实质改造）：所有人机交互提示输出为 stdout NDJSON 事件流，stdin 改收 JSON 指令。不带该参数时保持 v1 交互 CLI 行为不变。规范见 [03-核心协议复用.md](./03-核心协议复用.md#8-json-events-事件协议规范) 第 8 节。
2. **导出既有纯函数**：v1 该文件无任何 export（纯 CLI）。改造时把 `CookieJar`、`buildCodex2apiOauthExport`、`normalizeProxyUrl`、`isRiskControlResponse` 等纯工具函数补上 `export`（函数体不动），供服务端直接引用（测活判定、导入文件解析等）。若不想动该文件，可在 `server/core/risk-control.mjs` 复制 `isRiskControlResponse`（约 10 行）作为共享工具，二选一。
3. **`console-server.mjs` 完全废弃**，其中的业务逻辑（号池流转、codex2api 客户端、任务调度、代理轮换重启）按本文档重写为模块。

### 3.3 完全重写

- 后端 HTTP 服务：`node:http` 手写路由 → Fastify 插件化。
- 前端：单文件 SPA → TypeScript + shadcn-admin 多页。
- 数据层：内存 Map + 零散 JSON → SQLite。
- 凭据存储：DPAPI/Keychain → AES-256-GCM 入库（见 [07-安全设计.md](./07-安全设计.md)）。

## 5. 数据流总览

### 5.1 账号生命周期（主数据流）

```
邮箱.txt 导入
    │  解析四段格式 + 三重查重（备用池内 / 主号池 / 远端 codex2api）
    ▼
备用号池(reserve) ──异步──► 拉邮件初始化：邮箱名 / 初始余额(We've added X credits÷25) / 封禁关键字
    │ 单选或批量「加入主号池」
    │  ① 再拉一次邮件确认未封禁 ② 创建 login 任务(email_otp 模式, 随机存活代理)
    ▼
登录任务(jobs) ──子进程 protocol-login──► OAuth tokens + codex2api 导入文件
    │ 成功: 查实时余额(backend-api/wham/usage) → 移入主号池(main) → 可选自动上传 codex2api
    │ 失败: 回备用池并记录错误
    ▼
主号池(main) ──批量上传──► codex2api（已有→PUT 替换凭据；没有→POST 新增）
    ▲
    │ 监控巡检(5min): codex2api error 账号
    │   ├─ 401/deactivated/banned → 移入废弃池(banned_401)
    │   ├─ 429/rate limit        → 移入废弃池(rate_limited_429)
    │   └─ 其他临时错误          → 自动重登修复(冷却5min) → 修复失败×2 → 移入废弃池
    │   └─ 主池可用数 < 阈值(可选) → 自动从备用池补号
    ▼
废弃号池(discard)（记录原因/时间/原始错误，支持手动移回主池或彻底删除）
```

### 5.2 代理数据流

```
批量导入(每行: 代理URL 或 代理URL----备注)
    → 去重入库(status=unknown)
    → 一键测活(并发5, curl_cffi 过 CF 访问 chatgpt.com) → alive / cf_challenge / dead + 延迟
    → 任何 OpenAI 相关任务启动时: 随机选一条 alive 代理 → 无则本机直连
    → 任务运行中连接失败累计 → fail_count≥3 自动置 dead
```

### 5.3 会话数据流

```
打开页面 → GET /api/v1/auth/session
    ├─ Cookie 有效 → 直接进入（30 天滑动续期）
    └─ 无效 → /login 输密码 → POST /api/v1/auth/login
         → 校验 scrypt 哈希(timing-safe) → 写 sessions 表 → Set-Cookie( HttpOnly/SameSite=Strict )
```

## 7. 与 v1 的行为对照（差异清单）

| 行为 | v1 | v2 |
|---|---|---|
| 页面结构 | 单页全塞 | 左侧菜单 9 个页面 |
| 登录令牌 | 进程内存 token，刷新重输 | Cookie 会话 30 天滑动 |
| codex2api 配置 | localStorage + monitor.json 明文 | DB 加密存储，GET 脱敏 |
| 代理 | 单输入框随任务传 | 独立模块，测活 + 随机选路 + 自动降级 |
| 备用号池 | 有（join 后直接上传 codex2api） | 有；加入主池默认不上传，改为主池统一批量上传（可配置加入后自动上传） |
| codex2api 异常账号 | 只自动重登修复 | 分类：401/429 → 废弃池；临时错误 → 修复；可选手动补号 + 自动补号 |
| 任务日志 | 内存 80KB 截断，重启全丢 | 落盘 `data/logs/<jobId>.log`，API 分页读 |
| 任务状态 | 内存 Map + job-meta.json 重建 | jobs 表，重启自动重排队 |
| 凭据 | DPAPI/Keychain（Linux 丢失） | AES-256-GCM 入库，全平台一致 |
| 子进程驱动 | stdout 正则关键字 | NDJSON 事件流 |
| CLI 交互式登录 | 保留 | 保留（`--json-events` 只是新增模式） |
