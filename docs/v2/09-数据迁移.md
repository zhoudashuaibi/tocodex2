# 09 数据迁移（v1 → v2）

## 1. v1 数据盘点

| v1 数据 | 位置 | v2 去向 |
|---|---|---|
| 备用号池 | `{OUTPUT_ROOT}/reserve-pool.json`（结构：`{version, accounts:[{email,balance,hasBalance,banned,bannedReason,status,jobId,importedAt,lastCheckedAt,fetchError}],updatedAt}`） | `accounts(pool=reserve)` |
| 任务产物（OAuth token） | `tmp/chatgpt-onboarding-console/<uuid>/codex2api-import-oauth.json` | `accounts(pool=main)` 的 `tokens_enc` + 复制到 `data/results/` |
| 任务元数据 | 同目录 `job-meta.json`（约 40 字段：email/status/last_error/attempt…） | 迁移参考（不整表搬运；v2 任务历史从零开始） |
| 登录断点 | 同目录 `login-checkpoint.json` | `data/checkpoints/<accountId>/login.json` |
| codex2api 监控配置 | `{OUTPUT_ROOT}/codex2api-monitor.json`（**含明文 adminApiKey**） | `settings.codex2api.config`（加密） |
| Outlook 取件端点 | `{OUTPUT_ROOT}/outlook-fetch.json` | `settings.outlook.fetch` |
| 账号凭据 | 系统 DPAPI（Win）/Keychain（mac）；Linux 无 | `accounts.credentials_enc`（见 §4 限制） |
| localStorage 前端配置 | 浏览器（codex2api 上传设置/代理/接码平台） | 手动在新 UI 重填（一次性） |

`OUTPUT_ROOT` 默认 `tmp/chatgpt-onboarding-console/`，Docker 部署为挂载的 `data/`。

## 2. 迁移脚本 `scripts/migrate-v1.mjs`

```bash
node scripts/migrate-v1.mjs --v1-root /path/to/v1/tmp/chatgpt-onboarding-console \
                            [--v1-data /path/to/v1/data]      # reserve-pool.json 所在（默认同 root）
                            [--dry-run]
```

幂等：以 email 为唯一键，已存在的跳过（`ON CONFLICT(email) DO NOTHING`），重复执行安全。

### 2.1 步骤

1. **settings**：读 `codex2api-monitor.json` → `codex2api.config`（base_url/admin_key/group_ids/监控参数；v1 的 `groupId` 单值转 `group_ids:[id]`；v1 `reserveThreshold` → `monitor.reserve_threshold`）；读 `outlook-fetch.json` → `outlook.fetch`。
2. **reserve-pool.json → 备用池**：逐账号 INSERT（email/initial_balance=v1 balance/has_balance/banned/banned_reason/imported_at/last_checked_at）；`mail_status`：v1 `status=fetch_failed` → `mail_failed`，否则 `ok`；状态 `joining` 的账号按 idle 处理（v1 任务已不可恢复）。
3. **任务目录 → 主号池**：遍历 `<uuid>/` 目录：
   - 有 `codex2api-import-oauth.json` 且 job-meta `result_saved=true`：
     - 解析 `accounts[0]`：`credentials.email` 为账号键；
     - tokens（access/refresh/id_token、chatgpt_account_id）→ 加密 `tokens_enc`；
     - `balance`：job-meta 若有 credit 字段带入，否则空（迁移后可批量刷新）；
     - 导入文件复制到 `data/results/legacy-<email-hash>.json`（保留可下载性）；
     - 若该 email 已作为 reserve 迁入 → **升级为 main**（主池优先，v1 join 完成语义）。
   - 仅有 `login-checkpoint.json`（中断任务）：复制到 `data/checkpoints/`，账号不入池（v2 不复活半程任务，人工重新发起）。
4. **凭据回填**（可选 `--with-credentials`，见 §4）。
5. 输出汇总：`主号池导入 X，备用号池导入 Y，跳过重复 Z，凭据回填成功 W/失败 V`。

### 2.2 判定规则细节

- v1 job-meta `status=completed` 但产物文件缺失 → 跳过并警告。
- v1 `auto_repair_blocked / isPermanentAccountFailure` 标记 → 迁移为 `auto_repair_blocked=1`。
- v1 导入文件 name 已带 `---N` 余额后缀的，解析 N 回填 `balance`（N 即美元整数）。

## 3. 迁移后动作清单

1. 新系统设置页：确认 codex2api 配置已带入（admin_key 显示掩码即成功）。
2. 主号池「批量获取余额」跑一轮，回填/校准 balance。
3. 代理列表批量导入 + 测活（v1 单代理配置作废，重新成池）。
4. 接码平台/Outlook 取件端点检查。
5. 观察 codex2api 监控一轮巡检结果正常后，停用 v1 服务。

## 4. 凭据迁移的限制

v1 凭据在 OS 级加密存储（Windows DPAPI `%LOCALAPPDATA%\toCodex2\credentials\`，macOS Keychain）：

- **同机迁移**（Windows→Windows 同用户 / macOS→macOS）：`--with-credentials` 可解密回填（脚本调用 v1 credential-store 逻辑，需要 v1 源码在同仓库历史中或复制其实现）。
- **跨平台 / Linux 容器 → v2**：无法解密，跳过；迁移汇总会列出「缺凭据账号」清单，这些账号：
  - 有 refresh_token（已入 tokens_enc）→ 仍可 refresh 授权/上传，无需密码；
  - 无任何 token → 标 `needs_reauth`，重新导入凭据或从备用池重来。
- v2 不再使用 DPAPI/Keychain（AES-GCM 入库），此后迁移无忧。

## 5. 回退

v2 迁移只读 v1 数据、写入独立 `data/tocodex2.db`，不修改 v1 任何文件 → 回退 = 停 v2、起 v1。两者可并行运行观察（但**不要同时**对同一 codex2api 开自动修复，避免双写冲突）。
